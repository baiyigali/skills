# 技术分享文章执行模板

# 版本：v1.0
# 更新日期：2026-09-27
# 版本说明：技术实践经验分享通用模板，四阶段执行、固定正文结构 + 事实核查协议 + 参考文章/话题标签收尾，输出公众号风格 Markdown（不配封面，封面走 article-cover-image）。

## 模板使用说明

1. 核心参数：可选传入【主题/素材要点】。有素材时直接从素材出发；无素材时从近期真实项目实践自主盘点选题。
2. 定位：价值来自**内容的准确性、体系化**和**方法的可复用性**。素材可来自项目实践、工作经验或公开资料，正文一律写成通用技术分享，与作者个人经历无关。宁可选题朴素，绝不虚构。
3. 执行规则：严格遵循「素材盘点选题 → 框架设计 → 事实核查 → 模板撰写」四阶段，不跳过任何一步；事实核查为硬性环节。
4. 输出标准：仅输出完整文章成品，隐藏所有中间检索、整理、思考过程；专业严谨、可直接复制发布。

## 固定文章结构（全主题适配）

### 标题
- 结构 = 主题 + 核心方法/核心结论，可带一个具体的数字或动作（如「三条规矩」「两个决策」「四步走」）。
- 专业调性是底线：准确描述内容，不用耸动式副标题、噱头式反问、渲染对立。

### 引言（1-2 段）
- 实践场景一句话交代（项目背景、规模、约束）→ 点出真实踩过的坑或欠过的账 → 引出本文要给的方法。
- 禁止空泛开场（「随着 AI 的发展…」这类万金油开头）。

### 一、背景与约束（或：为什么这么做）
- 交代决策时面临的真实约束（预算、人力、合规、时间），约束决定打法。
- 先列「什么不能做」，再谈「什么能做」。

### 二、核心实践拆解（2-4 个小节，本文主体）
- 每小节 = 一个决策点或一组动作：为什么 → 怎么做 → 结果如何。
- 多方案对比必须用表格（维度 × 方案），对比维度选读者真正关心的（成本、心智负担、维护量、风险）。
- 配置、命令、规则文件给可直接抄走的最小可用版本。

### 三、踩坑与教训（可选并入上节）
- 每条教训 = 现象 → 根因 → 修正方法 → 通用判断标准。
- 优先写「付出了真实代价」的坑；已经解决的问题才写，未解决的如实标注。

### 四、实操模板 / 检查表
- 把全文方法压缩成可勾选的清单或可复制的模板（规则文件、配置片段、检查表）。
- 这是文章被收藏和转发的核心资产，必须具体到动作级别。

### 五、结尾
- 收束方法论价值（一两句升华，不堆口号）+ 引导转发互动（一句话即可）。

### 参考文章
- 列正文实际引用或强相关的文章/官方文档标题，**只写标题，不写链接**，一般 3-6 条。
- 只列真正支撑过正文论断的来源；官方文档优先于社区博客。

### 话题标签
- 参考文章之后另起一行，附适合公众号的话题标签（#开头，5-6 个，覆盖技术栈与人群）。
- 话题标签之后不附加任何署名、推广或引导关注行——文章以话题标签收尾即止。

## 事实核查协议（硬性，成稿前逐条过）

| 信息类型 | 处理方式 |
|---------|---------|
| 实操类素材（命令/实测/决策） | 可用作素材与校验来源；正文写通用技术分享（「一般怎么做」「典型场景是」），不绑定作者个人经历，不得把推断包装成实测 |
| 外部事实（平台政策/法规/参数/日期） | WebSearch 多源交叉验证，≥2 个独立可靠来源；正文注明依据；单源或低质来源 → 谨慎措辞或删除 |
| 推断与观点 | 明确作为观点表述（「我的判断是」），不与事实混写 |
| 用户实测经验 | 与网络信息冲突时以用户实测为准或复述确认 |
| 敏感信息 | 凭据/内网 IP/客户信息一律脱敏化名，成稿后全文复查一遍 |

典型案例：「平台 X 不要求备案/资质」这类准入断言属于高危区——必须检索官方帮助文档或一手公告验证，不能从单点经验或推断落笔（2026-09 实战教训：搜狗/360 站长平台的备案要求均与直觉相反）。

## 写作硬性要求

1. 通用技术分享视角，通俗接地气；专业术语翻译成大白话，讲清边界与适用场景；面向有一定基础的从业者与感兴趣的大众读者。
2. 段落简短，小标题加粗，多用表格、清单；md 加粗片段开头、结尾不得包含标点符号（标点放在 `**` 外面）。
3. 客观克制，观点跟着证据走；区分功能、安全、合规三层后果；不夸大收益、不渲染对立。
4. 不编造经历、数据、案例、引用；无法确认的信息标注说明或删除。
5. 仅输出完整文章成品，不输出中间检索、整理、思考过程；输出格式为 md，禁止 doc/docx。
6. 文件命名 `技术分享_NN_主题.md`，保存到约定交付目录；目录已有其他命名体系时沿用现有体系。
7. 篇幅参考 1500–2500 字；**必须有"实操模板 / 检查表"一节**，具体到动作级别。

## 代码块可读性（公众号受众）

- 单个代码块尽量 ≤15 行；能用目录树、伪代码、配置片段替代完整实现的就不贴完整实现。
- 每段代码前必须有一两句白话说明它在干什么，代码后补一句"为什么这么写"。
- 不连续堆长代码块：手机一屏装不下的代码等于没写。
- 复杂实现只留主干，砍掉分支与异常处理，或改写成注释式说明。

## 引用研究与数据的三条纪律

1. 写论文的总结论，不能只挑对自己有利的分组数字；整体结论是"无显著提升"就必须写出来。
2. 标注样本量与是否统计显著；不显著的要说"差异不显著/样本有限"。
3. 区分一手论文与二手转述；二手数据回到原始论文或官方来源核对，核不到就改谨慎措辞或删除。
