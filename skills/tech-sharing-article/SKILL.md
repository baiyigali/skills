# 技术分享文章

## Overview

把技术实践经验或公开技术知识，提炼成体系化、可复用的公众号技术分享文章。角色定位：资深工程师兼技术博主。全程四步：**① 选题 → ② 收集材料 → ③ 整理分析与事实核查 → ④ 按固定模板撰写**。

与追热点类技能（it-hotspot-article 等）的区别：本文章的价值来自**内容准确、体系化**与**方法可复用**，不依赖时效热点；宁可选题朴素，绝不虚构。素材可以来自项目实践、工作经验或公开资料检索，正文一律写成通用技术分享，与作者个人经历无关。

## Workflow

### 1. 启动：确认参数（只问一次，缺省全自主）

- **交付目录**：询问一次文章要保存到哪里。用户未指定时默认保存到当前工作目录下的 `articles/技术分享`（不存在则创建）。**不得写死带用户名或工具专属的绝对路径。**
- **指定主题**：用户已给出主题或素材要点时，从该素材池提炼主题后进入阶段①；未指定则从素材池（近期项目/会话、热搜、热点）自主提炼最优 1 个主题，向用户简要报告选题与理由（1-3 句）后直接继续，不等确认。
- **篇数**：默认 1 篇。用户要求多篇时按「批量模式」执行（见文末）。
- **文件命名**：`技术分享_NN_主题.md`（NN 两位递增序号；交付目录已有同系列文件时取最大序号 +1）。

### 2. 阶段①：选题（从素材池提炼主题）

用户提供的素材、热搜榜单、热点事件、项目记录，都只是**选题输入池**——如同热搜搜到的一堆网页，不会全部都用。要做的是从池子里**提炼出值得写的主题**（一句话能说清写什么、给谁看），而不是照单全收素材；素材里的具体小点只是主题的一个切面，文章不局限于它。

主题评估标准：

- **有认知增量**：方案对比、踩坑分析、成本权衡，或对普遍误区的拆解；
- **方法可复用**：读者遇到同类场景能直接照做，能产出清单、模板或对比表；
- **有普遍误区或认知缺口**：多数人默认做法是错的或次优的；
- **红线**：涉及不能公开讨论的项目、涉密内容、真实凭据与内网信息，一律脱敏或排除；企业/客户信息可化名。

选不出可核实主题时不硬写——如实报告并请示换方向。

### 3. 阶段②：收集材料

围绕选定主题做**体系化检索**，而不是只围着素材里那个小点打转：

- 覆盖主题全貌：主流方案横评、不同规模/场景下的适用性、常见坑与官方最佳实践；
- 用户素材只算一条线索，其结论同样要用外部资料验证或补充；
- 检索结果随手记要点（含来源），供阶段③归并与核查。

### 4. 阶段③：整理分析与事实核查（硬性环节，不可跳过）

先把材料归并、去重、搭成本篇骨架（固定文章模板见 `references/article-template.md`，撰写前必须完整阅读；多方案对比优先设计成表格），再对文中全部事实性论断做分级核查：

1. **实操类素材**（命令、实测结果、项目决策）：可用作素材与校验来源；正文按通用技术分享写法（「一般怎么做」「典型场景是」「常见的坑是」），与作者个人经历无关。不得把推断包装成实测。
2. **外部事实**（平台政策、法规条款、产品参数、统计数据、生效日期）：必须用 WebSearch **多源交叉验证**，至少两个相互独立的可靠来源（官方文档/一手公告 > 权威媒体 > 社区博客）；写进正文时注明依据。只有一个来源或来源可信度低时：改用谨慎措辞（「多方反馈」「存在被拦截的风险」），或直接删除该论断。
3. **推断与观点**：作为观点明确表述（「我的判断是」「推论是」），不与事实混写。
4. **用户实测经验是重要校验源**：用户亲测结论与网络信息冲突时，以用户实测为准或复述确认，绝不默认网络文章正确。
5. **禁止虚构**：不编造经历、数据、案例、引用；无法确认的信息要么删掉要么标注说明。

### 6. 阶段④：按固定模板撰写

严格遵循 `references/article-template.md` 的固定结构与写作硬性要求。要点摘录：

- **标题**：主题 + 核心方法/结论，专业调性优先，不做标题党、不刻意制造反差；
- **引言**：实践场景 → 踩过的坑或欠的账 → 引出本文要给的方法；
- **正文**：分层拆解，多用对比表和清单，每节给可操作的结论；
- **结尾**：收束价值 + 引导转发互动。

#### 写作风格（固定不变）

- 通用技术分享视角，通俗接地气；专业术语翻译成大白话，讲清边界与适用场景。
- 面向有一定基础的从业者和感兴趣的大众读者，不是写给顶尖专家。
- 排版：小标题加粗、分段简短、多用表格与检查表，适配手机阅读。

#### 硬性规则

- 客观中立，观点克制，结论跟着证据走；区分**功能、安全、合规**三层后果。
- 不夸大收益、不渲染对立；选题含金量是流量的来源，不靠叙事技巧博眼球。
- 禁止输出 word doc/docx；除文章内容外不输出多余头尾。
- **实操模板 / 检查表视主题选用**：主题本身适合沉淀成清单或模板时才写，且要具体到动作级别；**不硬凑**——为凑结构而生硬加的清单不如没有。
- **参考文章 3–6 条，只写标题不写链接**，只列真正支撑过正文论断的来源；官方/一手优先于社区博客。

#### 代码块可读性（公众号受众）

- 单个代码块**尽量不超过 15 行**；能用目录树、伪代码、配置片段替代完整实现的，就不要贴完整实现。
- **每段代码前面必须有一两句白话**：说清它在干什么、解决什么问题；代码之后补一条"为什么这么写"。
- 不要连续堆多个长代码块。读者是手机屏幕，一屏装不下的代码等于没写。
- 需要展示复杂实现时，只保留主干，把分支、异常处理、参数解析等砍掉或写成注释式说明。

#### 引用研究与数据的三条纪律（踩过坑）

引用论文、报告、统计数据时必须做到：

1. **写论文的总结论，不能只挑对自己有利的分组数字。** 若某研究整体结论是"没有显著提升"，就算分组里有一组是正的，也必须把整体结论写出来。
2. **标注样本量与是否显著。** 样本小、差异不显著的，要说"差异不显著""样本有限"，不能写成确定结论。
3. **区分一手论文与二手转述。** 二手博客转述的数据要回到原始论文/官方来源核对；无法核对的改用谨慎措辞或删除。

#### 正文隐私与可移植

- 正文不得出现本机绝对路径、仓库名、账号/凭据、内网地址等私有信息；需要举例时用泛指（`<技能目录>`、`某平台`）。
- 涉及具体项目时，企业/客户信息化名；成稿后全文复查一遍。

### 6. 收尾

- 文末以话题标签收尾，**不附加任何署名、推广或引导关注行**。
- 用 present_files 将 .md 呈现给用户。
- 本技能只产出 .md，**不感知也不调用封面**；用户需要封面时配合 `article-cover-image`（文章落盘后单独调用），发布时配合 `wechat-article-publish`。

#### 收尾自检（逐项勾选，不通过就改到通过）

- [ ] 结构齐全：引言 / 背景与约束 / 核心拆解 / 踩坑与教训 / 结尾 / 参考文章 / 话题标签（检查表一节有则必须具体到动作级，没有不算缺）
- [ ] 参考文章 3–6 条、只写标题无链接；话题标签 5–6 个
- [ ] 全部外部论断已多源验证；研究类论断写的是总结论、标了样本与显著性
- [ ] 每个代码块 ≤15 行，且前面有白话说明
- [ ] md 加粗片段的首尾不含标点符号（标点放在 `**` 外面）
- [ ] 全文无本机绝对路径、仓库名、账号凭据等私有信息
- [ ] 篇幅落在 1500–2500 字区间（低于 1200 字说明展开不够）

## 文件命名与既有体系

默认命名 `技术分享_NN_主题.md`。**若交付目录中已存在同系列的其他命名体系（如 `NN-主题.md`、`主题.md`），沿用现有体系**，不要为了套模板重命名已有文件——系列一致性比命名规则本身更重要。

## 批量模式

用户要求多篇时：每篇独立走完整四阶段流水线，**选题互不相同**（维护已用选题清单）；顺序执行、互不引用上下文结论；全部完成后汇总每篇的选题、文件路径、发布状态。

## 常见问题

| 现象 | 处理 |
| --- | --- |
| 近期没有可写的真实实践 | 如实报告，请示换方向；不虚构经历硬写 |
| 外部论断只有一个来源 | 改谨慎措辞或删除，不硬写为事实 |
| 网络信息与用户实测冲突 | 以用户实测为准或复述确认后再落笔 |
| 素材含敏感信息（凭据/内网/客户） | 脱敏、化名或排除后重查一遍全文 |
| 多篇批量时选题撞车 | 维护已用选题清单，换维度重新切入 |
